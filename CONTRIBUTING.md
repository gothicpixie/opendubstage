# Contributing

Thanks for helping. This project cares about three things more than features:

1. **Restraint is the product.** In sound post, the best processing is often the least. A change that processes more,
   adds more sound or cuts deeper needs evidence that listeners prefer it, ideally from a blind A/B, and not only a
   better metric.
2. **Rules are checked by the machine.** Every default is a named, documented parameter, and every behaviour that
   matters is pinned by a test. Where a tool has an independent checker (`foley.rules.check`,
   `mix.transitions.check_transitions`, `qc`), keep the checker independent of the code it checks.
3. **No private material, ever.** Tests use synthetic signals generated at test time. Example media must be public
   domain or CC0/CC-BY, with provenance in a `SOURCES.md` next to them.

## Setup

```bash
uv venv .venv --python 3.12
uv pip install --python .venv/bin/python -e ".[dev]"
make verify
```

`make verify` must pass before you open a PR. It is fast (seconds), offline and deterministic. CI runs the same target
on Linux and macOS for Python 3.10–3.13, with `ffmpeg` installed. Tests that need `ffmpeg` skip cleanly without it.

## Adding or changing a tool

- One module per tool, with a module docstring that states the method, the schema of any JSON it reads or writes, and
  why each default has the value it has (cite a standard, a spec or a measurement).
- Core dependencies are numpy, scipy and soundfile only. Anything heavier (torch, model weights, platform SDKs) goes
  behind an optional extra in `pyproject.toml`, is imported lazily, and is never needed by the test suite.
- Give the module a `main(argv=None) -> int` and register it in `opendubstage/cli.py` `TOOLS`.
- Add synthetic tests under `tests/`. Assert the property you care about (for example "bit-exact outside the region",
  "the band drops by the configured amount", "the checker finds no violation") rather than a snapshot of numbers.
- When a default number changes, say why in the commit body.

## Foley rules and sound classes

See the foley-specific guidance in [docs/foley-rules.md](docs/foley-rules.md):
- Add rule parameters to `Rules` (or `levels`). Enforce them in `plan()` and re-check them independently in `check()`.
- Sound classes name one action, material, place and distance. The prompt lint rejects cartoon drift.
- Backends document their code licence, their **weights licence** and whether commercial use is allowed, both in the
  backend's docstring and in NOTICE.

## Data and privacy

- Never commit recordings, transcripts, photographs, names or project files from productions you are working on.
- Never commit API keys or tokens. Backends read credentials from the environment at run time.
- Model weights and audio generated by non-commercial models are not committed. `vendor/`, `fx/`, `stems/` and audio
  files are git-ignored.

## Commit style

Use small commits with imperative subjects ("Add phrase-safe fade clamp"). Explain *why* in the body.
